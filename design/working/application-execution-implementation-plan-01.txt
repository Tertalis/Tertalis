1. STEP 2 - G8 AND TERMINAL JOBS
================================

1.01. EDIT backend/context/codeEntryContext.py
    _MemoryFacade.close aborts still-open nested transactions at any depth,
    innermost first, through the internal CommittedValueTransaction handles
    instead of the facade abort that requires a valid context. Already
    resolved ones are skipped; real cleanup errors are collected, not
    suppressed, even when invalidation has already begun (CP-8.01).

1.02. EDIT backend/application/applicationRuntime.py (runJob)
    Every failure path of an admitted Job records a terminal Job: if
    unit.finish or the IO abort raises, the Job is failed with the primary
    capability error and every cleanup error attached as evidence, the
    OrchestrationUnit outcome is recorded as failed where possible, and the
    Job carries an authority disposition (resolved | unresolved |
    partially-accepted, CP-8.02); a cleanup failure is also raised as a typed
    error after the Job is terminal. Rejected requests create no Job.
    Existing quarantine (execution-resource UNKNOWN) is unchanged.

1.03. TESTS
    NEW  tests/backend/application/test_openTransactionFailure.py: the G8
         reproducer from ai-workflow/knowledge/ai-buddy-g8-open-transaction-
         traceback.txt (capability opens a nested transaction and raises):
         Job ends Failed with the primary error, state unchanged, disposition
         resolved, next Job runs; nested depth 2-3; children already
         committed or aborted are skipped; an injected cleanup failure yields a
         terminal Job, disposition unresolved, primary and cleanup evidence,
         and no subsequent Job is claimed safe; IO commit failure after memory
         acceptance -> partially-accepted.


2. STEP 3 - BUILDING BLOCKS
===========================

2.01. EDIT backend/orchestration/runtime.py (Job)
    - wait(timeout=None) -> bool, Condition on the Job lock, notified at
      terminal publication (CP-10.02)
    - execution ownership: beginExecution()/endExecution(); an owned Job
      becomes dispatch-eligible only at endExecution(); a standalone Job at
      terminal publication
    - addDoneCallback(callback): dispatch now if eligible and outside any
      execution boundary; otherwise queue for eligibility (CP-10.03)
    - per-thread deferred dispatch list flushed by the outermost execution

    exceptional exit alike.

3. STEP 4 - EXECUTOR CORE
=========================

3.01. NEW backend/application/executor.py (ApplicationExecutor)
    - created inactive; activate() starts the worker (step 5 decides when)
    - submit/wake/pause/resume/stop/snapshot/cancel(jobId) (CP-4.01, 4.06,
      4.07); admission closed on stop or unsafe
    - execution scope (applicationRunId, jobId) set around each admitted Job;
      the runtime consults it for admission and rejects nested top-level
      Jobs (CP-3.02)
    - selection (CP-4.02), coalesced step opportunities and per-Job events
      (CP-4.03), wake generation (CP-4.04) separate from clock generation
      (CP-4.04a), cancelled step -> one fresh opportunity (CP-4.07),
      phases/control (CP-4.05)
    - unsafe: cancel queued Jobs observably, refuse submit/wake/inspection,
      resume cannot clear it (CP-8.03)
    - step directive validation and outcome classification (CP-6.02, 6.03)
    - outer failure boundary: recoverable fault vs unsafe (CP-8.02)
    - waits on a Condition with clock-derived timeouts, reconciliation at
      most every 60 s (CP-11.02)
    - stop(timeout): close admission, cancel unstarted queued Jobs, wait for
      the running Job, join the worker; StopOutcome complete/incomplete;
      retryable (CP-7.01, 7.02)
    - callbacks dispatched by the worker after runJob returns (CP-10.02)
    - tracing of phases, admissions, outcomes, faults (no payloads)

4. STEP 5 - LIFECYCLE AND HOST INTEGRATION
==========================================

4.00. NEW termination contract (CP-16): ApplicationRuntime.terminate(timeout)
    with a single cleanup owner (live -> terminating(owner) -> terminated |
    incomplete), used by ApplicationRuntime.stop/close, RuntimeHost
    closeApplicationRun/stop, standalone teardown and post-publication
    activation failure; destructive cleanup and the existing preflight
    decorators run only after the executor stop completes.

4.01. EDIT backend/application/lifecycle.py and backend/packs/runtime.py
    Validate the declaration after the defining AppPack's registrations are
    published (capability exists, owned by that AppPack, invocable as a Job);
    create the inactive executor; failures are activation failures (CP-2.02).

4.02. EDIT backend/runtime/runtimeHost.py
    - _initialize: activate the executor after _register and after leaving
      the host lane (CP-13.04); executor ownership transitions under the
      executor lock, activate after stop is a no-op (CP-13.02); worker-start
      failure after publication runs terminate (CP-13.03)
    - closeApplicationRun: stop the executor first, outside the host lane;
      if incomplete, keep the run registered and its resources, report typed
      incomplete; otherwise continue with today's close (CP-7.03)
    - stop: close host admission and snapshot runs under the lane, then stop
      executors outside it before closing execution resources; runs with
      incomplete executors stay registered, the shared services and
      resources they need stay open, stop reports incomplete and stays
      retryable (CP-7.03a)
    - configurable executor stop wait (default 30 s)

4.03. EDIT backend/application/lifecycle.py: standalone create/load activate
    the executor after _execute returns (CP-13.01).

4.04. TESTS (NEW tests/backend/application/test_executorLifecycle.py,

    invalid declaration rejected at activation; close with incomplete stop

5. STEP 6 - AI BUDDY ADOPTION (Tertalis-AI-Buddy)
================================================

Precondition: an independently accepted exact Tertalis SHA containing steps
2-5, adopted explicitly (protocol 12.13).

5.01. pack/manifest.json declares "application": {"step": "aiBuddy.step@1"}.

5.02. pack/codeEntry.py
    a. aiBuddy.step@1 runs one phase per call by calling the existing phase
       functions directly inside its own Job (no nested Jobs, no independent
       transaction authority; one transaction per step as today per phase).
    b. Phase order: process a generated inference (unless held by the output
       breakpoint) -> execute a prepared one (unless held by the prompt
       breakpoint) -> prepare. Returns "now" after progress, "idle" at a
       breakpoint or with nothing eligible, "at" the next due time.
    c. Scheduling computes the next due time (notBefore, periodic, expiry,
       intention lifetime); idle steps stop writing lastSeenAt on every check.
    d. Outbox: the step never marks delivered and the executor thread never
       delivers. The host adapter delivers on its own thread: it reads
       pending entries through inspection when a Job completion tells it the
       outbox may have changed, delivers them, then submits
       aiBuddy.outbox.acknowledge@1 (through id) as a Job. One delivery is in
       flight at a time and entries at or below the highest id already
       delivered and awaiting acknowledgement are not delivered again, so no
       duplicate concurrent delivery happens. After a restart, delivered but
       unacknowledged entries are delivered again (at-least-once, as today).
    e. Debugger state is semantically run-scoped: aibuddy/debug carries the
       applicationRunId it belongs to; a new run ignores and replaces it
       (breakpoints off unless the launcher asks, no pause). It is still
       physically saved with Application state like any other value; only
       its meaning is limited to its run. Pause ids include the run id, so a
       pause id from an earlier run is always stale.
       Breakpoint actions (mode, continue, replace prompt/output) are
       capabilities submitted as Jobs and keep the pause-id conflict rule.
    f. Time from ctx.clock (payload "now" accepted for tests).

5.03. host/buddyLoop.py becomes a host adapter: submits input and developer
    requests, reads through inspection, mirrors snapshots and Job completions
    into DriverEvents, cancels the running inference Job for interrupt, keeps
    the managed llama.cpp mitigations; its thread, queue, 0.25 s polling and
    imitated quiescence go (pause stands in for quiescence until G6).
5.04. host/frontendBridge.py: Invocations become submissions or inspection
    reads; loop flags from the executor snapshot.
5.05. run.py: no loop thread; quit uses executor stop with the managed-server
    wait rule; reports incomplete shutdown instead of exiting silently.
5.06. TESTS: harness with ManualClock and Job waits; checkpoint A-H adapted;
    new step-outcome, due-time sleep, breakpoint-as-idle, restart-clears-
    debugger, outbox acknowledge-after-delivery tests.


6. RISKS
========

6.01. Shutdown reordering in RuntimeHost touches lock ordering shared with
execution-resource cleanup; step 5 must keep the existing ER cleanup reporting
and tests intact.
6.02. Moving runJob callback dispatch to an outer wrapper must not change the
behaviour of existing callers that do not register callbacks.
6.03. AI Buddy's step consolidation is the largest consumer change; phases
keep their code, only sequencing moves.
