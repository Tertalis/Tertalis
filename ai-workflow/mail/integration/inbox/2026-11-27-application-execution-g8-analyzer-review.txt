REQUEST / INFORMATION
Do not accept step 2 yet. Corrections:

G8-R1: cleanup-only failure can be reported RESOLVED.
CodeEntryContext.invalidate attaches invocationCleanupErrors only if
sys.exception() is not None. Otherwise it raises ExceptionGroup or a
single critical BaseException. runJob._terminateJob only reads the
invocationCleanupErrors attribute and cannot distinguish that cleanup-only
failure from an ordinary capability failure. If memory/IO abort succeeds,
the Job reports resolved, empty cleanupErrors and no JobCleanupFailed,
despite actual invocation cleanup failure. This contradicts CP-8.02.
Deterministic reproduction: register a successful handler, inject an
OSError in invocation workspace.close (or another invocation cleanup
action independent of transaction abort), run the Job; assert terminal
Failed, UNRESOLVED, cleanup evidence, typed failure. Ensure ordinary
capability ExceptionGroup is not incorrectly classified as cleanup.
The critical-only branch also drops the remaining cleanup errors.
Represent cleanup evidence explicitly on every path, not solely through
attributes on the primary exception.

G8-R2: nested invocation cleanup evidence is overwritten or silently lost.
invalidate assigns primary.invocationCleanupErrors = tuple(errors); nested
capability calls can unwind the same exception through multiple contexts,
each with independent failing cleanup. The outer assignment discards the
inner evidence. Failure to assign attributes is silently swallowed.
A handler can also catch a nested invocation exception; determine how
unresolved cleanup survives that catch at the actual Job boundary.
Use execution-owned evidence or equivalent robust aggregation; preserve
all errors, primary identity and quarantine. Tests: nested invocation
inner and outer distinct cleanup failures; caught inner failure cannot
produce falsely resolved/successful Job; cleanup-only multiple errors.

G8-R3: unsafe subsequent admission is not contained.
The completion report explicitly defers enforcement to executor step 4.
However, current caller-driven runs have no executor, and G8 acceptance
review explicitly required no unsafe subsequent caller-driven execution.
runJob currently records PARTIALLY_ACCEPTED after memory commit and IO
failure and returns; no runtime admission guard is added. Reproduce using
existing IO failure test, then restore IO commit and attempt unrelated
writer Job on same runtime. A clean later transaction is not proof of
reconciled prior authority. Establish run-scoped unsafe containment for
unresolved/partial authority, independent of the optional executor, or
obtain explicit design-owner decision to change this requirement.
Preserve inspection/termination and existing quarantine as appropriate.
Test subsequent admission refusal before any new transaction/handler
execution, including non-opted-in runs. Do not invent automatic recovery.

G8-R4: exceptional boundary and early failure coverage.
runJob now catches BaseException but jobExecutionBoundary resolves False
on all such exceptions except JobCleanupFailed. For an interrupt after
authoritative memory acceptance (e.g. KeyboardInterrupt from IO commit),
the Job records authoritativeStateAccepted=True and PARTIALLY_ACCEPTED,
then re-raises the original interrupt; LLM scope sees False. Preserve
actual acceptance evidence on exceptional exit, without swallowing
interrupts or bypassing quarantine. For internally-created Jobs also
ensure caller has recoverable terminal evidence. Add deterministic tests
for IO open failure before unit.start, unit start failure, independent IO
abort and unit cleanup errors, interrupts before and after commit, and
ordinary success/failure compatibility. Existing test injects IO commit
failure only as an ordinary Exception.
Do not claim every admitted exit covered until boundary-level failures and
these cases are tested. Existing start/cancel race remains assigned to
step 3 tryStart, not a new step 2 blocker.
